# Plan: the 68040 and the A4000

Status: **spec, not started** (2026-10-18). Progress goes in
`progress.md` as each phase lands.

## Goal

`--cpu 68040` and an **A4000** preset that boots an A4000 Kickstart
(3.1 40.68 or 3.2 for the A4000) to Workbench 3.x with:
- a 68040 with its FPU and MMU (and the 68LC040, with no FPU);
- AGA and 2 MB chip RAM (both exist already);
- motherboard fast RAM, managed by Ramsey;
- the A4000's IDE interface;
- Zorro III, with a Zorro III fast RAM board;
- the battery-backed clock.

The work is ordered so that each phase can be tested on its own, with a
machine that already exists before the A4000 does.

## Where things stand

| Area | Today | What the A4000 needs |
|---|---|---|
| CPU models | `Model68000`, `Model68020`, `Model68030` (`m68k/m68020.go`, `m68k/mmu030.go`) | `Model68040` |
| Address bus | 24 bits everywhere: `m68kmem.MaxAddress = 0xFFFFFF`, the Mapper wraps at 24 bits | 32 bits for the 030/040 machines |
| MMU | 030: TC/CRP/SRP/TT0-1, any table layout, format $B frames, restart on RTE | 040: TC/URP/SRP/ITT0-1/DTT0-1, fixed 3-level tables, format $7 frames |
| FPU | 68881/68882 as float64, all seven formats (`m68k/fpu.go`) | the 040's FPU: a subset, a new FSAVE frame, single/double-rounding opmodes |
| Caches | not emulated; CACR stored | still not emulated; CINV/CPUSH accepted, 040 CACR bits |
| Expansion | Zorro II Autoconfig at $E80000 (`amiga/autoconfig.go`) | also Zorro III config space at $FF000000, boards at $40000000+ |
| IDE | Gayle at $DA0000/$DE1000 (`amiga/gayle.go`, `amiga/ide.go`) | the A4000's IDE at $DD2000 |
| RAM | chip, slow, Zorro II fast | motherboard fast at $07xxxxxx, Ramsey at $DE0000 |
| Clock | Oki MSM6242 at $DC0000 (`amiga/rtc.go`) | the A4000 has a Ricoh RP5C01 at the same address (battclock handles both); the Oki will do at first |
| Timing | 68000 cycle tables, `--cpu-speed` as a percentage of a 7 MHz 68000 | a 25 MHz 040 averages ~1.5-2 clocks per instruction: a speed setting, not a cycle table |

## Phase 1: the 32-bit bus

The prerequisite for everything else, and useful by itself: the A3000
has motherboard RAM at $07xxxxxx too, and AMIX could have more memory.

- Make the address width a property of the Mapper (and `maskAddr`)
  rather than a package constant: 24 bits by default, 32 for the
  030/040 machines. The 68000 and the 68EC020 keep wrapping at 16 MB.
- `Mapper.Map` takes the full 32-bit range. The linked list of mappings
  is fine for a few more entries, but check the cost of a lookup in a
  sparse 4 GB space (`TestTimingProfile`); add a top-byte index if it
  shows.
- Audit the `& 0xFFFFFF` in the Amiga code (`hdboard.go`
  `peekBytes`/`pokeBytes`, and others) and the DMA controllers (A2091,
  A2065), which are 24-bit Zorro II devices and should stay so.
- Where Kickstart probes above 16 MB on a 32-bit machine, unmapped
  space must still float (open bus); check the 030 MMU's
  physical addresses go through unchanged.
- The ROM appears at $F80000 only, in the first 16 MB. Confirm from the
  A4000 ROM's reset code that nothing expects it mirrored higher up.

**Tests:** Mapper tests at 32 bits (map above 16 MB, no wrap, open bus
up there); existing suite unchanged at 24 bits; the A3000 preset still
boots AMIX.

## Phase 2: the 68040 CPU (`m68k/`)

New file `m68k/m68040.go` (and `mmu040.go`), `Model68040 Model = 3`,
with `is040()`. The 040 is the 030's user instruction set; what
changes:

### Instructions
- **MOVE16** (all five forms: (Ax)+,(Ay)+ and the absolute ones), 16-byte
  aligned line moves.
- **CINV / CPUSH** (DC, IC, BC; line, page, all): privileged no-ops,
  since the caches aren't emulated.
- **PFLUSH (An), PFLUSHN (An), PFLUSHA, PFLUSHAN, PTESTR (An), PTESTW
  (An)** in the 040 encodings ($F5xx). The 030's PMOVE/PLOAD/PTEST
  forms ($F0xx) take the F-line exception on an 040: exec and the
  MMU libraries rely on that to tell them apart.
- Gone on the 040, so F-line or illegal: the 030 MMU instructions above,
  and the coprocessor interface (cpGEN etc. for IDs other than 1).
- **MOVEC** registers: CACR ($002, the 040's bits: DE bit 31, IE bit 15),
  TC ($003), ITT0/ITT1 ($004/$005), DTT0/DTT1 ($006/$007), MMUSR ($805),
  URP ($806), SRP ($807). CAAR ($802) is illegal on the 040. Exec's CPU
  probe (MOVEC to the new registers, catching the illegal-instruction
  trap) must find an 040 and set `AFF_68040` in AttnFlags: that is the
  first acceptance check.

### Exceptions
- Stack frames: format $0 (four words), $1 (throwaway, for interrupts
  with M set), **$2** (six words, with the instruction address: CHK,
  CHK2, TRAPcc, TRAPV, trace, divide by zero, unimplemented FP),
  **$3** (FP post-instruction), **$4** (unimplemented FP / FP disabled,
  with the effective address and PC), **$7** (access error, 30 words).
- Address errors: data accesses may be misaligned (as on the 020/030);
  only an odd instruction address raises one.
- RTE accepts formats $0, $1, $2, $3, $4 and $7, and takes the
  format-error exception for the others.

### The 040 MMU (`mmu040.go`)
- TC: E (enable, bit 15) and P (4 KB or 8 KB pages, bit 14). The walk is
  fixed: three levels, 7/7/6 bits of index (4 KB pages) or 7/7/5 (8 KB),
  from URP or SRP by the S bit. Four-byte descriptors only: table
  (UDT), page (PDT, with U, M, WP, S, CM, G, U0/U1), indirect, invalid.
- ITT0/1 and DTT0/1: transparent translation by address base/mask and
  S field, with a cache mode. Instruction fetches use ITT, data DTT.
  These are what the A4000's 68040.library uses (chip RAM not
  copyback-cached), so they matter more than the tables.
- Separate instruction and data ATCs, flushed only by PFLUSH. Unlike
  the 030, writing TC/URP/SRP does **not** flush them; software issues
  PFLUSHA itself, and the emulation should do the same.
- PTEST fills MMUSR (the physical page, R, T, W, M, S, CM, G, U, B).
- A fault takes an access error with a format $7 frame. The 040's own
  model is "restart with pending write-backs": the frame's SSW and
  write-back fields let the handler finish stores. The emulation can
  keep the 030's approach (undo the instruction, restart from the
  start on RTE) provided it reports no pending write-backs in the
  frame. Confirm against the frames 68040.library and any virtual
  memory software (e.g. GigaMem, VMM) read.
- The decoder's `Translate` hook (from the 030) carries over; it needs
  the instruction/data distinction it already has via function codes.

### The FPU
The 040's FPU does in hardware: FMOVE, FMOVEM, FADD, FSUB, FMUL, FDIV,
FSQRT, FABS, FNEG, FCMP, FTST, FSAVE/FRESTORE, plus the new
single/double-rounding opmodes (FSADD/FDADD, FSMUL/FDMUL, FSDIV/FDDIV,
FSSUB/FDSUB, FSSQRT/FDSQRT, FSABS/FDABS, FSNEG/FDNEG, FSMOVE/FDMOVE).
Everything else (FSIN, FCOS, FETOX, FLOGN, FMOD, FREM, FINT, FINTRZ,
FGETEXP, FGETMAN, FSCALE, FMOVECR, packed decimal) traps to the
**unimplemented FP instruction** exception (vector 11, format $4), and
68040.library (or the FPSP) emulates it.

Decision to make: **implement the full set natively by default** (the
emulator already has it; software runs whether or not 68040.library is
loaded) and offer `--fpu-strict` that traps the unimplemented ones, for
testing the libraries. Either way:
- FSAVE writes the 040's frames: idle is `$41000000` (version $41,
  size 0), null is 0. Exec and 68040.library recognise the FPU from
  this (`AFF_FPU40`), so it must be right.
- `--fpu none` with `--cpu 68040` is the 68LC040: every FP instruction
  takes the F-line vector (11) with a format $4 frame. Check that this
  is what 68040.library expects.

### Timing
Don't model 040 cycles. Make `--cpu-speed` default to a value for a
25 MHz 040 (measure against a known benchmark, e.g. SysInfo's
Dhrystones: an A4000/040 reports ~18-20 MIPS) and charge CPU chip-bus
accesses as now.

**Tests (`m68k/m68040_test.go`, `mmu040_test.go`):** MOVE16 forms and
alignment; MOVEC registers and the illegal ones; 030 MMU opcodes
F-line on the 040; each frame format and RTE of each; the 040 table
walk (4 KB and 8 KB, U/M updates, WP, S, invalid at each level); TT
registers; PTEST/MMUSR; FSAVE idle frame; FSADD/FDADD rounding; with
`--fpu-strict`, FSIN traps with a format $4 frame. If SingleStepTests
publishes 68040 vectors, run them as the 68000 suite is.

**Machine test, before the A4000 exists:** an A1200 with a 68040
(`--cpu 68040` with `kick32a1200.rom`), as with a Blizzard 1240.
Kickstart must report an 040 (SysBase AttnFlags), Workbench 3.2 boots,
SetPatch loads 68040.library, and a program using FSIN runs.

## Phase 3: the A4000 machine (`amiga/`)

Each part as its own file, as the A3000's parts are.

- **`ramsey.go`**: Ramsey's registers at $DE0003 (control: page mode,
  burst, wrap, RAM size, refresh) and $DE0043 (version: $0D in the
  A3000, $0F in the A4000), and the motherboard fast RAM below
  $08000000 (`--mbram MB`: 0, 4, 8 or 16 on the A4000). Kickstart sizes
  it by probing down from $08000000; confirm how from the A4000 ROM.
- **`gary.go`** (or in the Ramsey file): the A3000/A4000 system
  registers at $DE0000-$DE0002 (bus timeout mode and enable, the cold
  boot flag). Kickstart reads these early.
- **`ide4000.go`**: the A4000's IDE interface. The drive registers are
  at $DD2000 + 4n (n = 0-7, so data $DD2000, status $DD201C), the
  alternate status at $DD3018 and an interrupt status register at
  $DD3020 (bit 7: the drive's interrupt), on INT2. Reuse the ATA drive
  from `ide.go`; only the decoding and interrupt register differ from
  Gayle. Kickstart's A4000 scsi.device (despite the name) drives it.
  There is no Gayle ID register on the A4000; confirm what $DE1000
  reads as.
- **`zorro3.go`**: Zorro III Autoconfig. Boards are configured in
  $FF000000 config space, as well as Zorro II at $E80000; the
  registers are the same nibbles but a Zorro III board takes a 16-bit
  base address write (A31-A16) and can be 64 KB to 1 GB. Boards land
  from $40000000. `--z3ram MB` adds a Zorro III fast RAM board.
  (Buster sequences the Autoconfig chain; nothing to emulate beyond
  presenting boards in order.) Confirm the register layout from the
  Zorro III specification and the expansion.library disassembly.
- **ROM:** 512 KB at $F80000. The A4000 Kickstart is a separate ROM
  from the A500 and A1200 versions; none is in `ROMS/` yet.
- **Clock:** keep the Oki at first; add the Ricoh RP5C01 if the A4000
  ROM's battclock.resource insists (it probes for both).
- **The preset:** A4000 = 68040 + FPU, AGA, 2 MB chip, 16 MB
  motherboard fast, IDE, clock. Add it beside the A3000 in
  `cmd/goamiga/launcher.go` and the CPU cycle there.

**Tests:** Ramsey and the RAM probe; the IDE registers and interrupt,
then Kickstart's scsi.device finding an ATA hardfile; Zorro III
Autoconfig of a RAM board (base address, size, `AvailMem` after boot);
`TestA4000Boot`: the A4000 ROM to Workbench 3.2 from IDE, with an 040
in AttnFlags, the motherboard and Zorro III RAM in the free list.

## Phase 4: polish

- Configuration screen: A4000 button, 68040 in the CPU cycle, the new
  RAM options.
- Save states: the 040 MMU and FPU registers, Ramsey, the IDE and
  Zorro III boards (`savestate.go`).
- README and the Status list in `progress.md`.
- Optional, later: the 68060 (a small step from the 040: no MOVEP,
  more unimplemented integer instructions, the PCR register); the
  A3000 gaining motherboard RAM from Phase 1; AMIX on more RAM.

## Things to find out first

1. What the A4000 Kickstart's reset code and exec probe, in order
   (Ramsey/Gary registers, CPU and FPU detection, memory sizing):
   disassemble it with `diag/disasm68k.py` as was done for AMIX.
2. The frames and MMUSR fields 68040.library reads: it decides what
   breaks if the emulation simplifies the access error frame.
3. Whether the A4000 ROM's IDE driver uses the interrupt or polls.
4. The Zorro III Autoconfig details expansion.library expects.

## Risks

- **The 32-bit bus touches everything.** Do Phase 1 alone and rerun the
  full suite (and AMIX) before starting the CPU.
- **Speed.** A 25 MHz 040 is ~3-4× the 030 preset's work per emulated
  second; check the host still keeps up (`TestTimingProfile`), and keep
  translation off the fast path when the MMU and TT registers are off.
- **No ROM to hand.** Phases 1 and 2 need only the ROMs already in
  `ROMS/`; Phase 3 needs an A4000 Kickstart.
